# 上板与调试

读取当前 AGENTS.md、操作指南、编程/串口脚本与待测位流的时序证据。
识别本工程的下载器、器件 ID、volatile programming 方式、UART、bootloader、
网络和系统环境。PDS、65420、0x00602899、COM17 和自研 bootloader 仅是案例；
在其他工程使用其配置，不要求修改现有工具链。Linux 验收步骤按目标系统替换。
按需读取 [JTAG 和启动经验](references/lessons.md)。用户或已有工作流授权
CRAM 测试即可执行，不反复索要同一授权；skill 本身不授予额外操作权限。
SPI/配置 Flash 始终按项目规定取得新的明确确认并核对器件/分区。

## 分层定位

1. 核对当前 USB/PnP 的 present 状态、错误码、下载器身份与串口；历史正常快照
   不代表当前连通。UART 和 JTAG 是不同设备，COM17 存在不证明 JTAG 可用。
2. 检查 JTAG server 进程、端口、可执行路径与命令行，重启已确认归属的服务。
   Windows 背景启动用隐藏窗口，独立目录保存 stdout/stderr，避免覆盖旧证据。
3. 用正确 Configuration Shell 单一会话 connect→scan→read ID。该项目常用
   127.0.0.1:65420、PG2L100H ID 0x00602899；实际端口和器件仍以当前工程为准。
   绝对 Tcl 路径避免 `-work_dir` 改变相对路径解析。
4. 仅在位流哈希/最终时序和器件链通过后 assign `.sbit`→CRAM program→read DONE。
   校验原生输出、Program success、DONE=1 与无 `E:`。任一步失败不运行依赖步骤。
5. 编程前开始串口捕获，按实际脚本保持 DTR/RTS；识别 bootloader 提示后再发送
   命令。115200 8N1 是既有配置，零字节只说明该时段没收到字符。核对 DDR=ready。
6. 由当前 bootloader 的 SD 或 bundled TFTP 装载匹配启动文件；不是 U-Boot。
   进入 root shell 后检查 GET_INFO、驱动/UAPI、模型/向量哈希，再跑精确功能与
   严格硬件计时。记录均值/分位数和完整计时边界，不把下载时间混进 NNUE eval。

更新可移动启动介质时，先核对用户指定盘符的实际磁盘、容量、总线与文件系统。
从明确的候选目录选整套启动合同，核对源清单，备份被替换文件；已有匹配文件可
保留。完成写入、文件/卷缓存刷新与逐项回读哈希，再由用户安全移除并返卡。
准备脚本若固定生产目录，不能用它代替候选部署。返卡和新系统启动须另外确认。

## 失败处理和证据

PDS 退出零仍可能报错；检查 log 和预期完成标记。`cfg_close` 可能使 server
自行退出，下次不要假设连接仍在。连接失败时可做一次有变量改变的控制扫描，
比较目录、会话和串口等条件；已知 USB 枚举错误持续且重启未改变时停止重复
下载，说明需要恢复线缆/端口/供电或驱动条件。只操作已准确识别的 USB 设备，
不盲目重启整个 USB 控制器或停止无关进程；权限不足如实记录。

每次尝试保存位流/向量/启动文件 SHA-256、工具输出、器件 ID、DONE、USB 状态、
UART、时间与退出状态。区分尝试编程、是否执行到 cfg_program、是否确认完成，
以及是否跑过板端作业。超时或缺 DONE 时不能将实际写入状态简单标为“未写”。
未执行模型时平均推理时间为未知，不用仿真折算补上。失败新候选不替换生产文件。

暂停后台服务做性能对照时，保存 PID 并确认进程实际退出；停止提示和 PID 文件删除
不等于后台线程已结束。若测量加入一次性计时初始化，在开始采集/清计数之前预热，
避免将探针启动或串口输出造成的丢样归因于硬件。功能计数可在显式原时钟对照中
核验；该对照的绝对耗时若未校准，必须另标为无效。

二进制串口更新先传小控制文件，校验 CRC、重复包、实际大小和最终哈希，再更新大载荷。
控制传输重试失败时核对 UART FIFO、驱动接收方式与发送节奏；有新变量再作对照，
否则采用已可用的 SD/网络路径。PTY 通过不代表真实串口通过，不执行未校验载荷。

有 bootloader 易失热加载机制时，可核对 DTS 保留区、实际文件末尾和所有 DMA 缓冲，
选择跨启动仍保留的空闲 DDR；先传控制文件，再在系统内只读取出并比对原始哈希。
普通设备 read 与 mmap 的支持可能不同，按系统已有工具选择；这种测试不等于更新启动介质。

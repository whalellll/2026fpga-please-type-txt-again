# FPGA 时序优化

组合可选指令与提频/加速器修复时，参考
[CPU120 Zbc/FC1 合并与原生检查案例](references/cpu120-zbc-fc1-merge.md)。

读取当前 AGENTS.md、构建脚本、约束、最终时序报告与原生控制台日志。
先识别器件、speed grade、工具版本、时钟、DDR IP 和已接受配置；将下述流程映射
到当前工具的约束、STA、位置导出和错误检查接口。PDS 使用 FDC/PCF/`.rtr`，
其他工具使用其原生格式，不要求复制 Pango 的 site 名、工具参数或频率。
处理 DDR 或构建流程时，按需读取 [PDS 与 DDR 经验](references/lessons.md)。

CPU 提频按[固定提频流程](references/frequency-workflow.md)逐门执行：
基线、诊断、冻结、正确性/综合、受控完整 PnR、最终 STA/覆盖、启动同步、
实板性能/并发、记录发布。资源或路由成为瓶颈时先优化资源再提频；
CoreMark 与实际模型性能分别验收，失败的内存映射隔离或并发不得被单项通过覆盖。
本工程 CoreMark 性能只约束 CoreMark/MHz：同轮全样本均值绝对下降最多0.05；
总分仅记录，不设总分不得下降的门禁。测试通过并推送后才制作该版本交付包，
普通修改、失败/中断候选及单独流程维护不逐次打包。每版交付完成后，把后续不再需要的
过程文件逐文件校验归档至H:，再移除G:副本；细则见固定提频流程开头的当前规则。
本工程Linux交付的启动同步必须产出完整配套SD包及完整流程，并完成独立解包后的
实卡SD启动验收；临时RAM辅助包只用于诊断，不能作为交付启动方案。

## 定位与实验

- 本工程优化时序时，优先缩短压力路径的组合链并降低扇出。资源与布线压力可控时，
  可复制逻辑或寄存器，按消费者分组驱动；也可将同一逻辑链甚至整个单元拆成两级。
  这些改动已获用户授权，按实际路径选择，不受历史案例“不加流水”的限制。
  检查实际副本/级间边界、资源和两级路径；新增延迟须验证事务顺序、握手/冲刷及
  周期与吞吐影响，满足现有性能合同后再以最终全角STA和实板验收。
- 本工程每轮提频的最终布线 STA 若目标 CPU 域最差 WNS < −0.5 ns，下一步先考虑
  资源占用优化，核对整机及模块资源、拥塞和布线延迟，再选择有证据的修改。
  详见固定提频流程；本轮已有的更严格资源优先要求继续适用。
- 本工程因最终WNS < −0.1ns转入资源优化时，保留用于时序收敛的打拍寄存器、
  级间边界及隔离扇出的必要复制/缓冲；不得为减少FF/LUT撤掉这些资源。
  资源改写不能引入长组合路径或大扇出。对照实际网表的寄存器边界、组合级数、
  扇出负载和路径延迟，发现退化先修改或拒绝候选；资源下降不能替代完整全角STA。
- CPU 有配对 Chisel 源码时，可直接在 Chisel 层调试、添加断言、差分测试和波形，
  优先从源码定位微架构问题；具体方法见固定提频流程中的“Chisel CPU 调试”。
  若本地缺少源码，先检查对应远程 Git 仓库；未找到匹配版本时，对照当前 Verilog
  补全 Chisel，并验证生成结果的功能与周期一致性后用于后续优化。
- 若逻辑簇接近满载或详细布线反复发散，先按模块剖析整机映射资源与连线压力。
  在固定功能和可接受性能边界内完成资源改写的正确性、周期、整机综合资源及
  CPU 关键路径检查后，再启动新一轮完整布线；不以连续换 seed 代替资源分析。
- 为失败路径记录 corner、起终点、时钟对、setup/hold、例外、skew、逻辑/路由
  延迟、扇出和实际位置。检查两个方向与相关 clock group，不只检查一条 WNS。
- 默认保持约定频率、时钟周期、I/O 和时序例外。需要功能改变或新例外时先证明
  它符合电路时序关系；不靠降频或 false path 达成“性能不变”的目标。
- 源码/约束冻结到独立候选目录，记录 SHA-256、seed、hold 参数和工具版本。
  同一条件下改变一个有证据支持的布局、逻辑或扇出因素，再比较全角结果。
- 严格 DDR 位置必须来自当前打包后的真实单元及导出位置，核对类型、site/FF
  槽和占用。旧单元名消失应查清映射；不用 `-no_check` 或猜测打包别名。
- 若构建重新 dev_map，要确保额外 PCF 在映射之后仍被追加。核对原生每条约束
  执行结果，再从最终 PNR 数据库导出实际位置；输入 PCF 自身不是生效证据。
- PDS 案例的输入脚本使用 `flow_input.tcl`；该 PDS 会导出 `impl.tcl`，更换项目名仍可能
  覆盖同名输入。检查运行前后输入哈希与命令数量。构建脚本假工具测试只证明
  脚本分支，相关工具行为还要有最小原生复现和完整候选构建。

## 每次交付维护时序优化工具

本工程每次交付均复核并维护本轮使用的时序分析/优化辅助工具，将可复用的报告解析、
关键路径/扇出/组合深度分析、寄存器边界检查和资源比较能力保存在正式源码入口。
随包保存工具源码、依赖/运行命令、版本与哈希、相关测试和维护记录，独立解包验证。
不强求每轮改代码；无需修改时记录核对范围和理由，未完成的维护明确待验。
具体步骤、现有工具入口和证据边界见[时序工具维护](references/tool-maintenance.md)。
维护范围包括微架构分析和源代码编辑：本工程`scripts/microarch_timing_tool.py`提供
绑定路径的分析、受限组合表达式复制以及具体拆级/逻辑编辑规格的隔离补丁输出。
先阅读项目`docs/Microarchitecture_Timing_Tool.md`，区分源码线索、编辑候选与已验证优化。

## 验收

区分 map、place/route、生成位流、STA 和板测。工具退出零且无原生 `E:` 才能
通过工具运行检查；PDS 配置工具可能报错却退出零。候选还须满足：

- 当前约束集合在工具要求的全部 corner/mode 上通过；PDS 标记为 `All Constraints Met`，慢/快 setup 与 hold 均无违规，
  检查 recovery/removal/pulse width 等最终 summary。
- 预期时钟周期和例外不变，资源未超容量；严格绑定的实际导出与请求完全一致。
- 逻辑改动通过精确输出与周期回归；新增流水时按事务核对结果、顺序和约定延迟，
  不把合法延迟变化误判为逐拍不等价，也不以此忽略丢失/重复结果。声明性能不变时提供周期证据。
- 上板用与报告和哈希一致的已接受位流，保持候选与生产分开。

不要将空报告、过期结果、只读映射 DB 的失败 PNR 或中断构建标为收敛。
失败候选保留失败原因，不推广它的 PCF 或位流；下一轮根据新的完整失败路径选
改动。长构建只停止已核对归属的本任务进程。按本地 TODO 的板测和交付条件收尾。
